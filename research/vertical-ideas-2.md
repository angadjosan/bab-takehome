## Does any beat model evaluations?

No. The strongest new options can match or nearly match its deterministic settlement loop, but none beats model evaluations overall.

Model evaluations remain the best choice because the buyer’s desired object is itself a hidden, runnable test; the seller’s claim can be narrowly and honestly verified in minutes; and the pass and slash paths are unusually easy to explain. The closest new ideas are API compatibility-regression tests and accessibility-barrier test cases, but both are somewhat less economically distinctive and easier to dismiss as ordinary bug bounties.

## Top two new ideas

### 1. API compatibility-regression tests

1. A seller agent lists an encrypted test claiming: “SDK v3.2 breaks OAuth refresh-token handling under this request sequence,” with a price and stake.
2. The buyer sees the target API version, redacted assertion, seller pass rate, and stake-to-price ratio, then locks payment.
3. The seller releases the decryption key; the buyer’s browser verifies that the plaintext package matches the on-chain hash.
4. A verifier runs the hidden test in a sandbox against a fixed API fixture and posts a signed failing-test result on-chain.
5. A passing reproduction releases payment; a non-reproducing test refunds the buyer and slashes the seller’s stake.

### 2. Accessibility-barrier test cases

1. A testing agent lists an encrypted browser test claiming that a checkout flow traps keyboard focus after address validation.
2. The product team buys based on the redacted flow, severity, price, stake, and seller’s settled-test history.
3. The seller reveals the committed test package after escrow is funded.
4. A verifier launches the stated site build in Playwright, replays the keyboard sequence, and checks the focus assertion.
5. The contract automatically pays the seller for a reproduced barrier or refunds the buyer and slashes the seller for a failed claim.
